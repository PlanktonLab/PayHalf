# 台北通「陪辦」— 長者線上申辦協辦功能提案（討論版）

> 狀態：整理中，待團隊共識後開工。
> 日期：2026-11-07

---

## 1. 一句話定位

> 讓里長、子女、親友或官方客服，能在**自己的裝置**上一步一步「帶著」長輩，
> 而所有資料的填寫、授權與送出，都只發生在**長輩本人已實名登入的台北通手機**上。

關鍵論點（也是對評審與資訊局最有力的一句話）：

- **不是代填，是陪填。** 送出的仍是「本人在本人裝置上的操作」，完全沿用台北通既有的實名驗證信任模型，不需要另外處理「代理人／委任」的法律問題。
- **協助者只有「導覽權」，沒有「資料權」。** 長輩的個資不會流到協助者的裝置上。

> 命名建議：介面對長輩用「陪辦」或「有人陪我辦」，對外說明用「協辦」。
> 避免用「代填」，因為「代」字在法律與觀感上都暗示資料和操作權轉移給他人。

---

## 2. 問題痛點

| 層次 | 長輩遇到的困難 |
|---|---|
| 入口 | 找不到要申辦的業務在哪裡，連「第一步」都進不去 |
| 導引 | 看不懂介面要他做什麼，不知道下一步在哪 |
| 內容 | 不清楚欄位要填什麼、格式對不對、要附哪些證件 |
| 信任 | 怕按錯、怕被騙，寧願跑一趟區公所或里辦公處 |

現況：線上申辦必須本人在台北通 App 內操作（因為實名驗證），所以旁人**不能**替長輩登入後代填；
但長輩**自己又不會操作**。我們要解決的就是這個落差。

---

## 3. 角色與裝置

| 角色 | 裝置 | 能做什麼 | 不能做什麼 |
|---|---|---|---|
| **長輩（申辦人）** | 自己的手機，已登入台北通並通過實名 | 同意配對、逐項授權、最後送出、隨時中止 | — |
| **協助者** | 自己的手機／平板／電腦 | 選業務、帶著走每一步、在自己畫面示範要填什麼、看到「欄位已填／未填」的狀態 | 看不到長輩敏感個資的內容、不能替長輩按授權、不能替長輩按送出 |
| **後端（市府）** | — | 配對、同步步驟、推播、稽核紀錄 | 不把長輩個資回傳給協助者端 |

協助者有三種身分，介面上用不同徽章呈現，給長輩判斷依據：

1. **里長／里幹事**：公務身分，由系統名單認證（demo 用預設帳號）
2. **家人／親友**：一般台北通實名用戶
3. **官方客服（1999）**：市府內部帳號

## 4. 情境流程（主流程）

```
協助者端                                     長輩端
────────────────────────────────────────────────────────────────
① 進入「協助他人申辦」
② 選擇要協辦的業務（例：敬老卡申請）
③ 找到長輩：
   a. 掃長輩手機上的 QR Code（建議主路徑）
   b. 或輸入姓名＋出生年月日＋身分證末四碼
                              ──► 後端比對、找到裝置、發推播 ──►
                                                ④ 首頁出現大卡片：
                                                「王大明里長 想陪您辦理
                                                 【敬老卡申請】，要讓他協助嗎？」
                                                 [好，請他幫我]  [不要]
                              ◄── 長輩同意，建立協辦 session ◄──
⑤ 協助者畫面與長輩畫面同步進入表單
   協助者看到每一步的說明與示範
   點「下一步」兩邊同時翻頁
⑥ 遇到需要個資的欄位（例：身分證字號）
   協助者端只顯示「等待長輩授權…」
                                                ⑥' 長輩手機跳出全螢幕授權：
                                                 「要提供您的身分證字號給
                                                  【敬老卡申請】表單嗎？」
                                                 ▸ 用途：核對申辦資格
                                                 ▸ 保存：至申辦完成後 X 年
                                                 ▸ 風險：此資料不會給里長看到
                                                 [同意提供]   [先不要]
⑦ 所有欄位完成 → 協助者端顯示「請長輩確認送出」
                                                ⑦' 長輩看到完整摘要，大字、逐項
                                                 [確認送出]   [我要再看一次]
⑧ 完成：兩邊都收到結果，長輩端留下「這次誰協助了我、提供了哪些資料」的紀錄
```

任何時候，長輩都可以按「結束協助」中斷，協助者端立即失效。

## 5. 資安、防詐與法規設計原則

### 5.1 資料最小揭露
- 協助者端**永遠不顯示**長輩個資的值，只顯示欄位狀態（未填／已填／待長輩授權）。
- 非敏感的流程資訊（目前在第幾步、還缺哪個附件）可以同步，讓協助者知道怎麼帶。
- 以「姓名＋生日＋末四碼」查找長輩時，後端只回傳「找到／找不到並已通知」，**不回傳任何資料**，並限制每日查詢次數、全部留稽核紀錄，防止列舉式撈資料。

### 5.2 本人同意鏈
- 配對一定要長輩在自己手機上按「同意」才成立，且畫面必須顯示**協助者的實名與身分徽章**。
- 每一項敏感資料（身分證、戶籍地址、銀行帳戶、健康資料）都是**獨立一次授權**，不能一鍵全部同意。
- 送出只能由長輩端觸發。
- Session 有時效（建議 30 分鐘無操作自動結束），結束後長輩端有完整紀錄可查。

### 5.3 防詐
- 配對卡片與授權頁都放固定警語（大字）：
  「市府與里辦公處**不會**要求您轉帳、提供密碼、提供簡訊驗證碼。」
- 若協助者是「家人／親友」身分，卡片用不同顏色並多一行：「此人不是公務人員，請確認您認識他。」
- 授權頁保留「我不確定，先打 1999 問」按鈕（沿用 App 既有 1999 入口）。
- 同一協助者短時間內大量發送配對請求 → 後端自動封鎖並通報。

### 5.4 法規對應（demo 要在介面上「查得到」）
- **個資法第 8 條**告知義務：每次授權頁要列出蒐集機關、目的、資料類別、利用期間與地區、對象、方式、當事人權利。這剛好對應我們的「風險／用途說明」區塊。
- **個資法第 15、19 條**：公務機關蒐集需有特定目的與法令依據 → 每個業務頁放「法令依據」連結。
- 協助者的行為紀錄屬**稽核資料**，長輩端提供「下載本次紀錄」。
- 因為是本人操作，**不涉及**民法代理或委任書，這是設計上刻意迴避掉的法律成本。

### 5.5 無障礙與長者友善
- 長輩端全部用大字（建議最小 20sp，重點 28sp 以上）、高對比、單欄、一頁一件事。
- 按鈕只有兩個，正向動作放大、放下方。
- 可選：語音朗讀（TTS）授權內容。

## 6. Demo 架構規劃

### 6.1 前端：Flutter Web，一個專案兩個入口
```
helper_demo/            （新建，不動原本 TownPass）
  lib/
    app/            角色選擇（我是協助者／我是長輩）
    helper/         協助者端：選業務 → 找長輩 → 同步導覽
    elder/          長輩端：仿台北通首頁 → 配對卡片 → 授權全螢幕 → 摘要送出
    shared/         色票（抄 TPColors）、字體（PingFang TC）、元件、表單定義
    core/           WebSocket 連線、session 狀態
```
- 配色沿用 `TPColors`：主色 `#5AB4C5`、輔色 `#F5BA4B`、灰階、紅色警示 `#D45251`，但卡片陰影、圓角、間距可以做得比原 App 更精緻。
- 長輩端的首頁刻意仿台北通現有首頁（Logo、底部導覽），讓評審一眼看出「這是在台北通裡」。
- 兩台裝置 demo：同一個 Flutter Web 開兩個瀏覽器視窗（或一台手機＋一台電腦）即可。

### 6.2 後端：建議 Node.js（Express + Socket.IO）
- 原因：即時雙向同步是這個 demo 的核心，Socket.IO 的 room 概念剛好對應一個「協辦 session」。Python FastAPI + WebSocket 也行，但要自己處理房間與重連。
- API 草案：
  - `POST /sessions`：協助者建立協辦請求（業務、長輩識別方式）→ 回傳 sessionId
  - `POST /sessions/:id/accept`、`/reject`、`/end`：長輩端回應
  - `WS /sessions/:id`：事件 `step.changed`、`field.requestAuth`、`field.authorized`、`form.readyToSubmit`、`form.submitted`
  - `GET /audit/:elderId`：長輩端查紀錄
- 資料全部用 mock（可沿用 TownPass 的 `assets/mock_data/account.json`），不接真實系統。
- 「推播」在 demo 中用 WebSocket 事件模擬；文件中說明正式版可接 FCM／APNs。

### 6.3 表單定義（資料驅動）
每個業務用 JSON 描述步驤與欄位，標記哪些欄位是敏感、需要長輩授權：
```json
{ "id": "senior-card", "title": "敬老卡申請",
  "legalBasis": "臺北市敬老卡發行要點",
  "steps": [
    { "title": "確認申辦人", "fields": [
      { "key": "name", "label": "姓名", "sensitive": false, "source": "account" },
      { "key": "idNumber", "label": "身分證字號", "sensitive": true,
        "purpose": "核對年齡與戶籍資格", "retention": "申辦完成後 5 年" }
    ]}
  ]}
```
這樣加新業務只要加一個 JSON，demo 可以同時展示 2～3 個業務。

## 7. 待確認的決策點（請團隊表態）

| # | 問題 | 我的建議 |
|---|---|---|
| 1 | 功能名稱用「代填」還是「陪辦／協辦」？ | 陪辦（對長輩）、協辦（對外） |
| 2 | 協助者能不能看到長輩已填的值？ | 不能看值，只看狀態；非敏感欄位（如電話）可討論 |

| 5 | Demo 選哪 1～3 個業務？ | 敬老卡申請、里民活動報名、（可選）租金補貼初審 |

| 7 | 要不要做語音朗讀？ | 第二階段，先把視覺做好 |
